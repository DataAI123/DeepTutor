00三十秒速览 TL;DR

DeepTutor 是一个“代理原生”（agent-native）学习辅导系统：三种入口（CLI / WebSocket / Python SDK）汇入同一个 Turn 运行时，由 ChatOrchestrator 路由到 11 个 Capability 之一，Capability 内部驱动一个最多 8+3 轮的 Agentic Loop（LLM 决策 → Tool Calling → 观察 → 再决策），全部过程通过 StreamBus 以 15 种事件实时流出并持久化，前端按序号重放渲染。

一句话记架构

入口 → TurnEngine → ChatOrchestrator → Capability（整轮接管）或 Tool（单轮调用），共享 StreamBus 事件流 + SQLite 事件日志。

当前状态判断

v1.6.8 处于收敛硬化期：近 10 个提交 8 个是 fix，聚焦 turn 生命周期正确性、RAG 可诊断性、mastery 会话身份、Windows 启动体验。

迭代最值得关注的三处

① 循环宿主 agents/loop/ 是所有能力的公共心脏；② 6+ 条并行 WebSocket 协议栈是最大结构债；③ knowledge.py(4231行)/ChatStateAdapter.tsx(2919行) 是修改半径最大的热点。

02一次提问的端到端时序 FLOW

以 web 端 chat 为例，从浏览器发出消息到答案落盘返回的完整链路（租约、fan-out 是理解本层的两把钥匙）：

  1. 客户端发送命令 — {"type":"message","protocol_version":"2.0","content":"...","capability":"chat",...} 进入 /ws（api/routers/unified_ws.py:41）。握手鉴权 → 强制 PROTOCOL_VERSION=="2.0" → pydantic 判别联合 ClientCommand 校验（api/contracts/turn_protocol.py）。
  2. 应用服务受理 — TurnApplicationService.start_turn（app/service.py）→ TurnRuntimeManager（按会话缓存的运行时组合体）。
  3. 准备阶段 — services/session/turns/request_preparer.py:94：模型校验、语言回填、能力路由（route_explicit_quiz_request）、人设与模型选择鉴权、工具白名单回填，然后 申请 turn 租约、store.create_turn，派发后台 asyncio 任务。
  4. 上下文装配 — turns/executor.py:138：ContextBuilder 拼出 对话历史与摘要，落盘附件并抽取文本，装载 memory/persona/skills/source 清单，最终在 全仓唯一的构造点（executor.py:801-899）生成 UnifiedContext。
  5. 编排路由 — TurnEngine.execute → ChatOrchestrator.handle（runtime/orchestrator.py:61）：查 CapabilityRegistry（能力名缺省为 chat，每个 turn 新建实例、无跨轮状态）→ 发首帧 session 事件 → 新建 StreamBus 并按 turn_id 注册进全局路由表（供 user_input 命令找回活着的 bus）→ 并行启动“能力执行任务”与“事件订阅生成器”。
  6. 能力执行 — ChatCapability.run → AgenticLoopPipeline.run → AgentLoop.run：见第 3 章的循环细节。
  7. 事件流式下发 + 落盘 — 每个事件经 TurnLifecycle._publish_live_event（lifecycle.py:598）盖 session/turn 戳、分配单调 seq、写入 SQLite turn_events 表（UNIQUE(turn_id,seq)）、推给所有实时订阅者。done 事件被暂存，答案落盘之后才发出。
  8. 收尾持久化 — executor 归一化 provider 响应态 → store.add_message(role="assistant") → 解析 turn 终态 → 发 done{status} → DONE 之后再生成会话标题（session_meta）。服务层特意定义 _POST_DONE_MAX_SECONDS=30，注释直言：“DONE 不是最后一个事件，租约释放才是诚实的流结束信号。”
  9. 断线重连 — 前端重连后发 subscribe_turn + resume_from:{lastSeq}；服务端先回放 SQLite 持久积压，再做 catch-up 重读，最后挂实时队列；若 turn 已终态但缺 done，合成 error+done 帧保证客户端状态机闭合（lifecycle.py:341-460）。
  10. 取消/异常 — 取消经 coordinator 命令队列下发给持有租约的 worker，execution.task.cancel()；executor 捕获 CancelledError 后以 shielded 方式保存部分答案，终态 cancelled。单个消费者掉线不会杀能力任务（orchestrator 的 finally 只取消“没人读流”场景）。

3.2 System Prompt 组装 — 为 Prompt Cache 而生的顺序设计

agents/loop/prompt_blocks.py · LoopPromptAssembler.blocks() 固定顺序：

general → runtime_context(只注入“天粒度”日期) → runtime_policy → loop.system(yaml)
→ 各 LoopExtension.system_block() → 侧栏/课程规范/学习者画像/人设 → partner 策略 → memory
→ tools(工具说明+KB) → skills → sources → extended_tools(deferred 清单) → notebooks → workspace
拼接：块间 "\n\n---\n\n"，每块渲染 "## <name>"，末尾追加语言指令(allow_user_override=True)
关键洞察：KB 预检索内容塞进 user 消息而非 system 消息；日期只精确到天。两者都是为了 system prompt 逐字节稳定，命中 provider 的 prompt cache。这是后续迭代必须守住的隐含契约。

3.3 每轮状态机：一次 LLM 流式调用 + 一个分叉

  1. 调用 — _call_llm()：stream=True，带 tools 与 tool_choice（缺省 auto；ask_questions 第 0 轮强制 initial_tool_choice="ask_user"）。流中断按 (0.5s, 1.5s) 退避重试；15 秒无输出发 reasoning_progress 心跳；AskUserDraftEmitter 在流式解析工具参数的同时就把问题卡片推给前端（用户不必等整轮结束）。
  2. 分叉 — 本轮无 tool_calls → 该文本即最终答案（call_role="finish"），经守卫检查后循环退出；有 tool_calls → 本轮文本降级为旁白（call_role="narration"，前端展示为“思考过程”而非答案）。
  3. 工具分发 — 三段有序执行：① rebinding_tools 串行（会改变本轮操作对象的工具，如切换会话/材料）→ ② 其余并发（上限 MAX_PARALLEL_TOOL_CALLS=8，批内按规范化 args 去重，重复调用替换为教学式 stub 文本）→ ③ PAUSE_LAST_TOOLS={ask_user, workspace_export} 永远最后执行（它们要呈现“已跑完的轮次状态”）。发 tool_call 事件时剥离 _ 前缀私有参数与 sensitive 参数。
  4. 观察回填 — 工具结果以 role=tool 消息 append 进 messages——这就是“观察”进入下一轮上下文的唯一通道。随后 _fold_context_checkpoint 做窗口折叠：超过 CONTEXT_WINDOW_GUARD_RATIO=0.9 时裁剪老工具结果并插入“已省略”提示。
  5. 协议修复 — 非 OpenAI 协议能力（如靠文本标签工作的模型）走 labeled_step.py：标签(THINK/TOOL/FINISH…)前的正文实时流成 thinking，违规输出用 progress 事件标注 protocol_violation 并重试修复。DSML 兜底同属此层。

3.6 ask_user：跨 4 文件的暂停-恢复

  1. tools/ask_user.py 返回 ToolResult(pause_for_user=…)（≤4 问、每问 ≤8 选项）；
  2. tool_dispatch.py 汇总为 DispatchOutcome(pause=True, pause_tool_call_id)，一个批次只允许一张待答卡；
  3. pipeline.py:1132 _await_user_reply_and_resolve()：发 pending_user_input 轨迹 → context.runtime.wait_for_user_reply() 挂到 lifecycle 的回复队列（WS 侧由 submit_user_reply 命令注入；跨模块则经 get_bus(turn_id).submit_input()）→ on_user_pause/on_user_resume 扩展钩子；
  4. 把答复重写进对应 role=tool 消息正文，并附 ask_user_resolved_directive（“继续原始请求，不要只回一句确认”）→ 循环 continue，turn 全程存活。IM 渠道语义不同：暂停时待发问题本身就是回复，用户下一条 IM 消息开新 turn（services/partners/runtime.py）。

3.7 结果出口与成本核算

所有能力收敛于 agents/_shared/capability_result.py · emit_capability_result()——它只做一件事：把 UsageTracker.summary() 塞进 payload["metadata"]["cost_summary"] 再发 RESULT 事件。UsageTracker（runtime/agentic/usage.py）三口进数：响应真值 usage（流式只取最后一帧）、无 usage 时按 chars/3.5 估算、BaseAgent 适配器手工上报；价格来自 logging/stats/llm_stats.get_pricing。一个循环内所有调用（旁白轮/结算轮/强制收尾/provider 重试/扩展预检索）汇入同一个 tracker；跨能力不合并。

04两层插件模型：Capability × Tool 与三种扩展口味 ARCH

4.1 协议契约

协议文件要点
TurnCapabilitycore/capability_protocol.py唯一方法 run(context, stream)；CapabilityManifest 声明 name/stages/tools_used/cli_aliases/request_schema/config_defaults。stages 声明与执行松耦合：声明只是元数据（给 UI/CLI），真实阶段由 async with stream.stage("planning") 上下文管理器驱动，二者无强制校验——加新能力时要自觉遵守。

三种口味一句话分工：TurnCapability = 拥有整轮；LoopExtension = 借用 chat 的整轮并注入行为；KnowledgeCapability（如 Obsidian/IMA）= 独占工具面的 LoopExtension（选中其 KB 时替换整个工具表，但保底保留 ask_user + workspace 四件套 + rag/kb_files）。

4.2 注册与懒加载

两级懒加载：ToolRegistry.load_builtins() 只登记 BuiltinToolSpec(name, "module:Class") 描述符，首次 get/execute 才 importlib 实例化（tools/builtin_specs.py，60+ 条目，含别名表 pdf→read_source、rag_hybrid/naive/search→rag(mode=…)，实例化时校验“目录漂移”）；CapabilityRegistry.load_builtins() 注册闭包工厂，每次 get() 新建实例。外部插件走 entry-point 组 deeptutor.extensions（旧 deeptutor.plugins 兼容并告警）。此外 ScopedToolRegistry 为多租户提供白名单强制层，注释直言“过滤清单不是闸门，execute() 才是唯一强制点”——因为模型可产出任意工具名。

14.3 迭代时必须守住的隐含契约（易被无意破坏）

  • Prompt cache 字节稳定：不要往 system prompt 注入分钟级时间/随机顺序内容；动态原料放 user 消息（§3.2）。
  • 事件即事实源：前端从 events 重算答案，新增事件类型要考虑 replay 路径与 UnifiedTurnClient 白名单映射。
  • execute() 是唯一强制点：工具权限只在 ScopedToolRegistry.execute 校验，任何绕过 registry 的直调都是漏洞。
  • DONE 不是最后事件：session_meta 在其后；客户端以租约释放为诚实终点（§02 步 8）。
  • 物理路径不出工作区：workspace 路径只存在于 runtime，不进模型消息/元数据/URL。
  • fail-open/fail-closed 的方向：管理员工具白名单读取失败=放行；用户能力探测失败=禁用。改动前想清楚属于哪类。

UnifiedContext每轮唯一上下文包：用户消息+历史+工具开关+KB/记忆/persona+不可序列化 runtime 回调。
Lease / Fencing Token（租约）turn 执行权的分布式锁（memory 或 Redis+Lua）；防止多 worker 双跑同一 turn、支持崩溃恢复。
Settlement（结算轮）探索预算耗尽后的收尾阶段：注入指令令模型停止调工具、基于已有观察强制作答。
Narration / Finish同轮 LLM 文本的两种角色：有工具调用时是“旁白”（前端展示为过程），无工具调用时是最终答案。
Progressive Disclosure（渐进披露）deferred 工具不进初始 schema，只留清单，模型 load_tools 现场加载——控制上下文占用。
RAGRetrieval-Augmented Generation：先检索知识库证据再让 LLM 基于证据作答；本系统 6 引擎可插拔。
Embedding（嵌入） / 向量库把文本映射为高维向量以做语义检索；换嵌入模型会产生 embedding_mismatch 标记待重建索引。
Prompt Cachingprovider 对逐字节相同前缀按缓存计费/加速；本系统 prompt 组装顺序与日期粒度为其让路。
Tool Calling / Function CallingLLM 以结构化 JSON 请求调用外部函数的机制；非支持模型走标签协议+DSML 抽取降级。
MCPModel Context Protocol：外部工具服务器标准；MCP 工具注册进同一 ToolRegistry 并属 deferred。
Knowledge Gate（达标闸门）mastery 按知识点类型定通关标准：memory/procedure 看测验分（0.9），concept/design 看 Feynman 式讲述。
间隔重复 / Feynman 式评估基于遗忘曲线安排到期复习 / 让学习者用自己的话讲解概念以证明理解。
Bwrap / Sidecar 沙箱Linux bubblewrap 命名空间隔离 / 独立 runner 容器执行；Windows 降级为清理环境的受限子进程。
Regenerate（重新生成）turn 层语义：以原用户消息的 request_snapshot 重放新 turn，新答案落盘成功后才删旧答案（原子替换）。
Replay / Resume（重放/续传）断线后按 after_seq 从 SQLite turn_events 补发缺失事件；终态缺 done 则服务端合成。
Fail-open / Fail-closed出错时放行 vs 拦停。本系统：管理员白名单读取失败 fail-open；用户能力/资源探测失败 fail-closed。
Partner接入 IM 渠道（Discord/Telegram/Matrix 等）的常驻 AI 伙伴，有独立 WS 与回合策略。
Contract Codegen（契约生成）后端导出 openapi/turn-protocol JSON → 前端生成 TS 类型，两端 CI 校验漂移。
